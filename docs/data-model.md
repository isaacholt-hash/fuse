# FUSE data model (P1)

The whole P1 schema, designed up front so shipped migrations never need patching. Each milestone builds only the tables it needs (the **Built in** column). Later tables and columns arrive as **new** migrations (`CREATE TABLE`, `ALTER TABLE … ADD COLUMN`); shipped migrations are never edited.

Requirement IDs refer to `docs/requirements.md`.

## Conventions (all tables)

| Rule | Detail |
| --- | --- |
| Primary key | `id TEXT` holding a **UUIDv7** (time-sortable, safe to create offline, works for P2 sync without renumbering). |
| Tenant columns | `workspace_id TEXT NOT NULL`, `user_id TEXT NOT NULL` on every table, including `workspaces` (where `workspace_id = id`) and `users`. Every query filters by `workspace_id` (SE-04). |
| Timestamps | `created_at`, `updated_at`: `INTEGER` Unix milliseconds, UTC. |
| Migrations | Run on their own connection with foreign keys off, so a migration can rebuild a table others point at (SQLite's documented 12-step way); `PRAGMA foreign_key_check` runs after, and any broken row stops the update. The database is backed up first (PL-11). |
| Deletes | Soft delete with `deleted_at INTEGER NULL` on user-visible records (threads, messages, projects, memories, artifacts), so P2 sync can propagate deletes. A purge job hard-deletes after the retention window. |
| Money | `INTEGER` **micro-dollars** (`cost_micro_usd`), never floats. |
| Tokens | `INTEGER NOT NULL DEFAULT 0`: `input_tokens`, `output_tokens`, `cached_input_tokens`, `cache_write_tokens`, `reasoning_tokens`. |
| Enums | `TEXT` with a `CHECK (col IN (...))` constraint. |
| JSON | `TEXT` holding JSON, only for open-ended data (capabilities, options). Never for anything we filter or sum on. |
| Foreign keys | Declared, with `PRAGMA foreign_keys = ON` per connection. Child rows of a soft-deleted parent stay; the UI hides them. |
| Secrets | **No table ever stores an API key.** Keys live only in the OS keychain (step 4). |

**Price versioning.** `data/models.json` has a `price_version` (the date its prices were verified, e.g. `2026-10-26`). Each priced row stores the `price_version` it was costed with plus the computed `cost_micro_usd`, so later price changes never rewrite history (CO-01).

The routing policy, tiers, model catalog and prices are **data files** in `data/`, not tables. User edits to them are saved as override files, not rows.

**`data/routing.json`** (M1 step 9, `src/routing/policy.ts`): three tiers in order (Cheap, Balanced, Best), each a list of `provider/model-id` from `data/models.json`; within a tier the app picks the cheapest model for the request's input size, ties going to `provider_preference`, then the chat's provider. `housekeeping` maps titles, classification, memory and summaries to a tier. `quality_floor` is the lowest tier allowed to answer per intent and complexity (RT-17). `rules` are first-match-wins (intent, complexity, capabilities, context size → tier, with a `reason` shown on the answer); the last must match everything. Neither a rule nor a floor may name Cheap: the file is refused at startup.

**Auto routing** (M1 step 10, `src/routing/classify.ts`, `src/routing/route.ts`): before each send a local classifier reads the question (length, code, attachments, keywords) as an intent and complexity. The first matching rule picks a tier, never below the floor. The cheapest model in that tier with a key and the needed capabilities answers. If none qualifies, the next tier up is tried; routing never moves down. The Cheap-model fallback for unsure classifications (RT-02) is not built yet. Settings → Routing test set scores the classifier against the imported prompts.

| Tasks (no new table, M5 step 5) | `memories` rows with `kind = 'task'`, project-scoped: `task_status` (`open`/`doing`/`done`/`dropped`) and `depends_on` (task ids). A task waiting on one that isn't done or dropped shows as blocked. Project settings → Tasks adds and edits them; a model may suggest one after a chat, which waits for review like any suggestion. Open and in-progress tasks go as context (`Task (to do): …`), never cut for budget (like decisions and constraints); finished ones don't. | PM-16 |
| `settings` | Key/value per user. Used now for `memory.suggest` (`on`/`off`) and `memory.budget_tokens` (default 1,500). Never keys. | PM-03, PM-04 |
| `threads.memory_injection`, `threads.memory_checked_at` | Memory on/off per chat, and the `last_message_at` the last memory check covered (a chat is checked again only after new messages). | PM-03, PM-04 |
| `memory_vectors` | M2: sqlite-vec `vec0` virtual table: `memory_id`, `embedding`. The embedding model and dimension are recorded in `settings`, and changing them triggers a re-index (MM-11). | PM-04 |

**Context assembler (M5 step 7, PM-18).** Every request is built in one place: `src/context/gather.ts` collects what the thread contributes (history with attachments, the summary of older turns, file excerpts and recalled chats on the question), and `src/context/assemble.ts` builds the system prompt in this order: app guides, instructions (global, project, chat), `<decisions_and_constraints>`, `<open_tasks>`, `<memories>`, `<earlier_conversation>`, edited artifacts. It returns each part with its sources (instruction levels, memory ids, artifact ids, file chunks). A chat with no decisions, constraints or tasks sends exactly what it did before the assembler (a snapshot test recorded beforehand). Send, edit, regenerate, retry, escalate and compare all go through it.

**Egress policy (M5 step 8, `0028_egress.sql`, SE-13).** `projects.privacy_mode` (`normal`/`local_only`/`cloud_only`) and `projects.allow_embeddings`; `egress_rules` (one row per provider, global with `project_id` NULL or per project; a project's rule wins; no row means allowed); `files.may_send` (a knowledge file kept on this device is never searched for a request or embedded). `src/context/egress.ts` turns these into a policy. It is checked by the router (blocked providers are dropped from the candidates, and the message says so), by every chat send in `streamAnswer` (a blocked provider gets nothing; the answer is an error that says why, logged as `egress`), by housekeeping (titles, summaries, memory suggestions, the classifier's second opinion), by embeddings, and by the context gatherer (no excerpts from kept files; keyword-only memory ranking when embeddings are off). Local only refuses every cloud send until local models arrive (M7). **The Rust transport checks again (M5 step 9):** every content-carrying request (POST) must carry a scope, `thread:<id>`, `project:<id>` or `global`. Adapters send it in an internal header that `providerFetch` lifts into its own field, so it never reaches a provider. `src-tauri/src/egress.rs` looks up the chat's project in the database itself, applies Local only, the embeddings switch and the provider rules, and refuses with `egress: <reason>`. The adapters turn that into a `blocked` error that shows the reason. A POST with no scope is refused. Model lists (GET) carry no content and pass.

**Linked repository (M6 step 3, `0029_repo.sql`, CA-01).** `projects.repo_root` is the coding agent's folder, resolved by Rust (`repo_check`) when linked, NULL when none; `projects.repo_read_sensitive` lets it read secret-looking files (`.env`, keys), and goes back to 0 on unlink. `src-tauri/src/repo.rs` reads the root from here for every list, read and search, so the frontend only ever names a project and a relative path. Paths must be relative, without `..`, and inside the root after following symlinks; `.git` and files the repository's `.gitignore` files exclude are skipped; reads are capped at 256 KB per part, with an offset for the rest; binary files are refused.

**Coding runs (M6 step 5, `0030_runs.sql`, CA-07).** `runs`: one task in a project's linked repository on one model (`provider`, `model`), its `mode` (`plan` = read-only for now), `status` (`running`, `paused`, `done`, `stopped`, `error`) with a plain-words `note`, `cap_micro_usd` (AG-05 default $1) and `spent_micro_usd`; optionally the chat and answer it shows in. `run_steps`: numbered model turns (their `text`, the provider's own turn as `native` JSON for replay, the `request_log` row and cost) and tool calls (`tool_name`, `tool_call_id`, `input` JSON, `output`, `is_error`). A run is resumed from its steps alone (`src/agent/run.ts` `historyFromSteps`). The same migration rebuilds `request_log` to allow the `agent` purpose.

**File changes (M6 step 6, `0031_run_changes.sql`, CA-02).** `run_changes`: one file a run created (`before` NULL), edited, deleted (`after` NULL) or moved (`from_path`), linked to its tool step, with `status` `applied` or `undone`. Undo puts `before` back and is refused when the file no longer holds `after`, so nothing newer is lost (`src/agent/run.ts` `undoChange`, `undoRun`). The same migration rebuilds `runs` so `mode` allows `ask` and `auto_edit` (CA-04). Rust writes are atomic (temporary file, then rename), never inside `.git`, never outside the root (the deepest existing folder is checked after symlinks), and skip secret-looking names unless the project allows them.

**Permissions (M6 step 8, `0032_permissions.sql`, CA-04, AG-04).** `projects.run_mode` is the mode a project's coding runs start in (`plan` read-only, `ask` before each edit and command, the default, or `auto_edit`: edits go ahead, commands ask). `project_commands` holds the commands you always allow in a project, matched exactly; destructive ones (force push, `rm -r`, hard reset, `sudo` and the rest in `src/agent/destructive.ts`) ask every time and can't be added. `run_steps.approval` records how each tool call was allowed (`auto`, `you`, `always`, `denied`), which Settings → Coding agent activity lists with the model and the run's cost.

**Run summaries (M6 step 9, `0033_run_summary.sql`, CA-08).** When a run's next request would pass half its model's window (at most 150k tokens), the Cheap tier (`purpose: summary`, priced against the run's cap) summarizes the steps so far into `runs.summary`, carrying any earlier summary forward, and `runs.summary_upto` marks the last step it covers. The loop then starts again from the task plus that summary; older turns aren't edited, because thinking signatures need an append-only history. Without a Cheap model the steps are listed instead. Runs still `running` when FUSE starts are marked `stopped` ("FUSE closed while it was working") and can be continued.

**Git (M6 step 10, `0034_run_branch.sql`, CA-05).** `runs.branch` is the `fuse/…` branch a run made for itself before its first turn, when asked to. Git tools run `git` and `gh` from Rust (`src-tauri/src/git.rs`) with an argument list (no shell), an allowlist of subcommands (git `status diff log add commit switch push rev-parse branch`, gh `pr create` and `pr view`), no config or command-injecting options, and prompts off. Status, diff and log go ahead in every mode; branch and commit ask in Ask and go ahead in Auto-edit; push and pull requests always ask and say they leave this computer.

**Run plans (M6 step 11, `0035_run_plan.sql`, RT-14).** With Auto routing, the cheapest Best model writes `runs.plan` (`runs.planner` names it) in a request of its own with no tools, logged as `agent` with tier `best` and priced against the run's cap; the loop then works on the routed model with the plan in its task. A tool loop stays on one model, so this is the only model change within a run, plus Cheap-tier summaries (step 9). A pinned tier or model does everything, with no separate plan.

**Run limits (M10 step 11, `0052_run_limits.sql`).** A stall watchdog beside the cost cap. `projects.run_cap_micro_usd`, `run_wall_minutes` and `run_idle_minutes` are what a project's runs start with; NULL means FUSE's defaults ($1, 120 minutes of work in all, 15 minutes without progress), and a run's own `capMicroUsd` (a schedule's, say) still wins. `runs.started_at` is when the run's current leg began (set at creation and again by Continue) and `runs.waited_ms` the time in that leg spent waiting for an approval, which counts toward neither limit: "Running for" and the wall clock measure `now - started_at - waited_ms`. A tripped watchdog stops the run the way Stop does (the stream or command in flight is aborted) and leaves the note "Stopped: no progress for 15 min." or "Stopped: ran for 2 h.". Stop always works: on HULK a stop request for a run the runner isn't running marks it stopped ("Stopped from another session."); on the desktop a run left "working" with nothing running it is marked stopped from its card.

**Two areas (M10 step 12, `0053_thread_kind.sql`, CH-19).** `threads.kind` is `chat`, `code` or `work`: chats live in the Chat area, Code and Work sessions in the Code area. The migration gave every thread that already held a run the kind of its last run; the rest are chats. New threads take the area they're written in (Work when the composer's Work switch is on in Code); a scheduled task's thread takes the task's kind, and a handed-over run's thread on HULK is `code`. Runs aren't exported, so an export written before 0053 restores every thread as a chat; later exports carry `kind` like any column. The same migration adds the columns steps 13 to 17 use, all NULL until then: `seen_at` (when the thread was last opened), `schedule_id` (the task it was made for), `handoff_from_id` ("Continue in Code", "Discuss in Chat") and a session's own `run_mode`, `run_branch`, `run_where` and `run_cap_micro_usd` (NULL: the project's default, then the app's). The open area and each area's last thread are per device, in localStorage (`fuse.area`, `fuse.lastThread.chat`, `fuse.lastThread.code`).

**Answers without a model (M7 step 2, `0036_project_no_model.sql`, LL-01).** `projects.answer_without_model` (on by default) lets fixed rules in `src/deterministic/handlers.ts` answer arithmetic, unit and date conversions, counts and JSON or CSV checks before routing. Such an answer is an ordinary assistant message from provider `deterministic` with the rule as its model, and it has a `request_log` row with purpose `chat`, the same provider and model, and cost 0. That row is the audit trail, and it counts as a cloud call avoided (LL-07). Only Auto sends with nothing attached are eligible, outside coding runs and compare mode.

**Shadow checks (M7 step 9, `0037_local_shadow.sql`, LL-09).** For 7 days after the local model is installed, about 1 in 10 housekeeping jobs it finished also runs, in the background, on the cloud Cheap model it would have fallen back to. That cloud call is billed and logged like any other. `local_shadow` keeps one row per check: purpose, the two models, both latencies, both reply lengths, and `same` (equal once spacing and case are ignored). It never keeps the text (LL-07). Nothing is checked when the project's policy blocks the cloud. Settings → Local model shows the count, the agreement rate and the median times.

**Lexical chunk search (M7 step 10, `0038_chunks_fts.sql`, LL-05).** `chunks_fts` is an FTS5 index over `chunks.text` with external content, like `messages_fts`. Insert, delete and update triggers keep it current, and it was rebuilt over existing chunks on upgrade. Files are searched by BM25 first; vectors (`chunk_vectors`), when they exist, are merged by rank. Token ceilings are data in `data/context.json`.

**Response cache (M7 step 11, `0039_response_cache.sql`, LL-06, RT-13).** `response_cache` keeps an exact-match key (SHA-256 of the model, effort, system prompt, messages, output format and project), `kind` (`chat` or `classify`), the project `scope`, the model that answered, the response, its original cost, the hit count, and `expires_at` (24 hours for chat, 30 days for classify). A hit writes a `request_log` row with provider `cache` at $0, and an answer from the cache is stored as a message from provider `cache`, with its author model as `model`. Expired rows are deleted when they're looked up. Delete everything clears the table. Its `DELETE_ORDER` now covers every table, guarded by a test.

**How memory v1 works.** Leaving a chat with new messages (or "Suggest memories now" in its menu) sends its transcript, capped to the newest ~24,000 characters, plus the saved facts to the housekeeping model: the cheapest Cheap-tier model (`data/routing.json`) with a saved key. The call is logged with `purpose: memory`. Before each send, in-use memories in scope (global, the chat's project, and ones kept for that chat only) go into the system prompt after the instructions. If they all fit the token budget they all go, otherwise the ones sharing the most and rarest keywords with the question (`src/memory/inject.ts`).

## Encryption at rest (M1 C2)

- **What's encrypted:** the database (`fuse.db`) is SQLCipher. `src-tauri/src/db.rs` owns the connection, and the frontend sends SQL through the `db_execute` and `db_select` commands. The SQL plugin was dropped because it can't pass a key to its connections.
- **The key:** 32 random bytes, used as a raw key (`PRAGMA key = "x'…'"`), kept in the OS keychain under the account `database-key`. The frontend never sees it, except as the recovery key (Settings → Recovery key: 8 groups of 8 hex characters).
- **Upgrading an unencrypted database (first launch):**
  1. The WAL is checkpointed.
  2. `sqlcipher_export` copies the database into an encrypted file.
  3. Row counts per table are compared.
  4. The encrypted copy is swapped in, and the unencrypted file and any unencrypted backups are deleted.
- **If the keychain has no key, or the wrong one:** the app shows a locked screen that takes the recovery key, and puts it back in the keychain.
- **Migrations:** the same sqlx migrations as before, so `_sqlx_migrations` carries over.
- **Not encrypted yet:** attachment bytes in `files/<sha256>` (follow-up).

## M0 migration plan (step 3)

`0001_init.sql` creates `workspaces`, `users`, `threads`, `messages` (including `parent_id`), `request_log`, `schema_meta`, plus indexes:

- `messages (thread_id, created_at)`
- `threads (workspace_id, last_message_at DESC)`
- `request_log (created_at DESC)`

It also seeds the default workspace and user with fixed UUIDs. Before each migration the app copies the database file to `backups/fuse-<timestamp>.db` (section 16, Data).

**Folders (M8 step 1, `0040_folders.sql`, WF-02).** `folders` is a folder FUSE may work in: its absolute path as Rust resolved it, unique per workspace, and `read_sensitive`. `project_folders` and `thread_folders` link folders to projects (used by all their chats) and to single chats. The migration moved each project's `repo_root` into these tables, so the project's first linked folder is its M6 repository. `projects.repo_root` and `repo_read_sensitive` stay in the table (migrations are forward-only) but are no longer read. Folders aren't exported: a path only means something on this computer.

**Run folders (M8 step 2, `0041_run_folders.sql`, WF-01, WF-02).** `runs` was rebuilt, the documented way, so that `project_id` can be null for a run in a chat outside a project, and so it has `kind` (`code`, or `work` from step 3). `run_folders` lists the folders a run works in, in order, each with the `label` its paths use when there are several (`notes/todo.md`), so continuing or undoing a run reaches the same folders. Runs from before got their project's first folder. The Rust commands (`repo_*`, `repo_exec`, `repo_git`) take a `folder_id` and read the folder's root from `folders`, never from the caller.

**Step images (M8 step 4, `0042_step_images.sql`, WF-03).** `run_steps.images` is a JSON list of `{sha256, mime}` for the images a tool step showed the model. The bytes are in the attachment store (`files/<sha256>`, encrypted), and each later turn of the run loads them and sends them with that step's result again.

**Document changes (M8 step 5, `0043_change_bytes.sql`, WF-04).** When a run writes a Word, Excel or PDF file, its `run_changes` row keeps readable text of the old and new document in `before` and `after`, for the diff. `before_sha` and `after_sha` name the bytes in the attachment store. Undo checks that the file still hashes to `after_sha`, then writes `before_sha`'s bytes back, or removes the file when `before_sha` is null.

**Organise plans (M8 step 7, `0044_change_batch.sql`, WF-06).** Each move in an approved plan is its own `run_changes` row (`from_path` to `path`), and all of them share a `batch_id`. Undoing any one of them undoes the whole batch, newest move first.

**Network grants (M8 step 10, `0045_network_grants.sql`, WF-07).** `network_grants` (scope `thread` or `folder`) say where sandboxed commands may use the network. A run gets the network when its chat or any of its folders is granted. The grants are added when you answer "Allow for this chat" or "Allow for this folder", or with the switch in Project settings → Folders, and removed with that switch.

**Flagged tool results (M9 step 4, `0048_step_flags.sql`, AG-10).** `run_steps.flags` is JSON, a list of `{why, passage}`, on a tool step whose output read like an instruction (null when none). Only reads and commands are checked. While a run has any, its later writes, commands and sends ask and can't be always-allowed; the activity log shows them.

**Tools switched off (M9 step 1, `0047_project_tools_off.sql`, AG-01).** `project_tools_off` has one row per tool a project switched off in Project settings → Tools. Every tool is on unless it has a row; runs outside a project have every tool, and the registry's core tools (`list_files`, `read_file`, `search_files`) are offered whatever the rows say. Read once per turn of a run.

**Folder knowledge (M8 step 11, `0046_folder_files.sql`, FK-07).** `folder_files` has one row per document found in a folder: its path, the SHA-256 and size of its bytes on disk, its modified time, and the `files` record that holds its extracted text. That record is linked to every project with the folder through `project_files`, so it's chunked and embedded like any knowledge file. A changed document gets a new file record, and the old one is unlinked and loses its chunks and vectors. A removed document loses its row and record links. `listProjectFiles` reports each file's `folderId` (null for uploads).
