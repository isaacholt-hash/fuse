# M9 — Tools and MCP (P2, part 2)

**Goal:** the rest of P2's agent Musts. Runs and chats can use more than files: they read the web, run Python on data, and call tools from MCP servers you add. Anything a tool brings back is treated as data. Instructions found in it are shown to you and never followed without asking (requirements §11, AG-01, AG-02, AG-03, AG-10; FK-08 and SE-10 come with them). It builds on M6's runs and approvals and M8's sandbox.

**Done when:** the recorded tools benchmark (step 11) passes on both providers. Its tasks are: answer from a web page read with `fetch_url`, chart a CSV with Python and return the chart, and use a tool from a local MCP server. The injection tests show that an instruction planted in a page, a file, a command's output or an MCP result is flagged and never acted on without your yes. Isaac then runs `pnpm tools:live` with his own keys.

**Out of scope:** the web app on HULK and background runs (CA-15, CA-16), sync (PL-04), scheduled tasks (AG-07), built-in connectors (AG-11, though any MCP server you add works), skills and hooks (CA-12, CA-13), subagents (CA-14), dictation (VI-01) and deep research (FK-12).

## Decisions (Isaac, 2026-10-31)

- **M9 is Tools and MCP**, because it finishes P2's Musts. The web app on HULK and background runs (CA-15) come after.
- **Where tools work:** in Code and Work runs, and in plain chat for the read-only ones (fetch_url, MCP tools marked read-only). Anything that writes, sends or spends needs a run, so it gets the run's approvals, plan and cost cap.
- **MCP:** stdio servers and remote HTTP servers (Streamable HTTP) with OAuth; tools only, not resources or prompts. Servers are added in Settings and switched on per project. Local servers run in the M8 sandbox, with no network unless allowed. Their env values and OAuth tokens live in the OS keychain, like API keys.
- **Code execution:** Python only in M9, in the M8 sandbox (bubblewrap or AppContainer), from a pinned Python downloaded on first use and checked by hash, the same pattern as M7's local model. It comes with pandas, numpy, matplotlib and openpyxl, pinned. Node waits, since `run_command` already covers it for Code runs. Not Pyodide.
- **Injection guard, two layers.** Every tool result reaches the model wrapped as untrusted data, saying what it is. Before a write, command or send that follows such a result, FUSE checks the result for instruction-like text (a fixed rule set, plus the local model when one is installed); if there is any, the approval shows the passage that may have caused the action. The local model can add a flag but never clear one, and nothing is blocked without telling you.

- [x] **2. `fetch_url` for runs and chat (AG-01).** The FK-06 reader in `web.rs` as a tool: public addresses only, after DNS and on every redirect; size and time capped; HTML turned into readable text. Read-only, so it runs without asking. The egress policy is checked before the page's text is sent anywhere.
  - Part 1 done (runs): Code and Work runs, read-only ones too, have `fetch_url` (kind read). A page comes back as its title, address and readable text, capped at 40,000 characters, and says when the page was cut. A page that can't be read is an error result, not a failed run. It isn't offered without the web reader or in a Local only project, since even an address leaves the computer. Its run card row reads "Read <address>".
  - Part 2 done (chat): a chat answer on a model that takes tools is offered `fetch_url`, unless there's no web reader, the project is Local only, or it switched the tool off. When the model calls it, FUSE reads the page and asks again with the result, for up to 3 rounds; then it must answer without tools. Each round is logged as its own request with its cost, and the answer's cost is their sum, so thread, project and month totals agree. The pages read are the answer's sources, which also keeps such answers out of the response cache. Project settings → Tools says the switch covers chats too.
- [x] **3. Tool results are data (AG-10, part 1).**
  - Every tool result reaches the model wrapped in `<tool_output tool="…" source="…">` (`src/agent/untrusted.ts`): a web page, a file or document in the user's folders, a command's output, git, or "a tool" for anything else. That's in run turns and chat rounds alike, on both providers, since it's built before the adapter.
  - A tag inside the content that would open or close the wrapper, in any case, is defused, so a page or file can't end it early and speak as FUSE.
  - The Code and Work guides, in every mode, and the system prompt of a chat whose model is offered tools, say what the wrapper means: data, never instructions. If it asks for something (a command, a change, a send, secrets, ignoring the rules), carry on with the user's request and tell the user what it asked.
  - The summary of a long run's earlier steps is told the same, so an instruction can't be laundered into "progress so far".
  - Tests plant "ignore your instructions" with a fake closing tag in a page, a file, a command's output and a document, and check each reaches the model inside one wrapper. Whether a model then ignores it is for the live run (step 11); step 4 adds the check that doesn't rely on the model.
- [x] **4. Flag what a tool result asks for (AG-10, part 2).** A rule set finds instruction-like text in tool results (commands to run, files to delete, addresses to send to, "ignore previous"). When a write, command or send follows a flagged result, its approval shows the passage and where it came from, and it can't be always-allowed. The local model, when installed, can add a flag but never remove one. Logged in the activity log. Also: a `fetch_url` whose address carries text from a file or an earlier tool result (a long query string, say) is flagged and asks first, since that's a way to send content out.
  - Part 1 done (flags):
    - `src/agent/injection.ts` has six rules: ignoring your instructions, speaking as the system or the user, running a command (including `curl … | sh` and encoded PowerShell), deleting files, sending something to an address, and showing secrets. Up to three flags a result, each with its line.
    - What reads and commands bring back is checked as each step is recorded; FUSE's own write results aren't. Flags are kept on the step (migration 0048, `run_steps.flags`), and the activity log shows "Flagged: …" on that row.
    - Once a run has a flagged result, every later write, command and send asks, in Auto-edit too and for always-allowed commands. The approval shows up to three passages and where each came from, and "Always allow" isn't offered: an "always" answer counts as one yes. The network question loses "Allow for this folder" the same way.
    - Ordinary files, logs and pages aren't flagged in the tests, but false alarms are possible; they cost a click.
  - Part 2 done (addresses and the local model):
    - A `fetch_url` address that carries text from something read earlier (any 24 letters and digits in a row that appeared in a result, URL-encoded or not), or that has a query over 200 characters, asks first in a run, with a card that says why. A denied one isn't read. An address the user wrote, or one that appeared whole in a result (a link on a page), doesn't ask.
    - Chat can't ask, so there such an address isn't read: the model is told why and to ask the user to open the page.
    - With a local model installed, what `fetch_url`, `read_file` and `read_document` bring in gets a second look when the rules found nothing. It can add a flag ("reads as instructions to the local model"), never remove one, and runs only on the local model, logged as a `classify` request.

- [x] **6. `run_python` (AG-03, part 2).** Runs a script in the M8 sandbox, in the run's folders, with no network unless allowed, and time and memory limits. ## Fixes

- [x] **F6. A model picked just before sending wasn't used (found 2026-10-31 by the Windows click-through test "switch models", which failed 8 of its last 27 runs).** Picking a model in a saved chat saved the pin, and the send read the chat's mode from the chat list, which only had the pin once it was saved and read back. On a slow database (1 to 2 s writes in CI), a message sent straight away went out on the old mode, while the picker already showed the new model. Now the picked mode is used at once for that chat, until the list has reloaded with it. A test holds the pin's save and checks the answer comes from the picked model. Not a test fix: it could happen to Isaac too.

- [x] **F7. Python's startup warning, and the test planner's reply (found by the PC tests, 2026-10-31).** In the Windows sandbox, Python can't look at the folders above its own, so every script's output started with "Failed to find real location of …python.exe" before running normally. That one line is now left out of what the model gets (a script's own output, even the same words later, is kept). The test build's scripted model also answered the planner, which asks without tools, with "run_python wasn't offered"; it now gets a plan.
  - **First PC run (2026-10-31, run 41230569635):** passed in 149 s with the Python install. The script itself took 41.9 s, mostly loading pandas and matplotlib cold (Defender likely scans the new files); later runs aren't timed yet.

## Notes

- The usual rules apply to each step: one PR, tests, a screenshot for UI changes, the secret scan, `cargo fmt --check` and clippy when Rust changes, CI green, then merge.
